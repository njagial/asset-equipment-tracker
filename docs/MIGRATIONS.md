# Database Migration Strategy

State: `uv run manage.py makemigrations --check --dry-run` must be clean at all
times (enforced in CI). Migrations are reviewed like code; generated by Django
5.2; applied via `python manage.py migrate` (both prod entrypoint & deploy).

## 1. Principles

1. **Source of truth is `apps/*/models.py`.** Never hand-edit migrations except
   to add data migrations or vendor-guarded operations (see section 3).
2. **Expand → Migrate → Contract.** Destructive changes (dropping columns,
   narrowing constraints) are done *after* all deployed code can live without
   the old shape, so a blue/green rollout never races an ALTER.
3. **Apps own their schema.** Each app has its own `migrations/`; cross-app
   dependencies are declared explicitly via `migrations.swappable_dependency`
   and first-party app dependencies (alerts + maintenance → inventory).
4. **Reversibility.** Every migration has a working `backwards` path except
   appends-only audit data; `squashmigrations` is considered after a release
   cut, never mid-release.

## 2. Rollout order (per release)

```
uv run manage.py makemigrations <app>   # commit generated files with the model change (same PR)
uv run manage.py migrate --plan         # review the planned statements
uv run manage.py migrate                # idempotent; applied on deploy (Docker entrypoint)
```

Deploy sequence for production environments:

1. CI builds image; `uv sync --frozen` pins dependencies.
2. Release job runs `python manage.py migrate --noinput` against staging → prod
   (single runner, Postgres advisory-locks serialize concurrent migrators).
3. Then new gunicorn/worker/beat containers roll; old containers keep serving
   with the post-migration schema (expand pattern keeps them compatible).

## 3. PostgreSQL-only operations (vendor-guarded)

`apps/core/migrations/0001_postgres_extensions.py` enables `pg_trgm` +
`btree_gin` for fuzzy search. The operation is **guarded by a vendor check**
(`schema_editor.connection.vendor != "postgresql"` → no-op), so the same
migration tree applies cleanly to SQLite dev/test environments. Follow the
same guard for any future GIN/expression/trigram indexes.

Performance-critical indexes from the spec (asset_tag unique, serial_number
unique, location, status, composite status+location) are declared in
`models.Meta.indexes` and travel inside the app's initial migration.

## 4. Data migrations

- Data migrations live in their own numbered migration and operate via
  `apps.get_model("label", "Model")`, never raw import of current models (so
  historical schema stays honored while older migrations replay).
- The `seed_demo` command is **not** a migration — demo/dev data never belongs
  in the deploy path.

## 5. Rollback policy

- **Code rollback:** migrations are forward-only during a incident; new code is
  rolled back to the previous deploy (schema stays — expand pattern).
- **Schema rollback:** only executed if a migration was never followed by
  dependent writes. `manage.py showmigrations <app>` + `migrate <app> <rev>`
  for targeted rollbacks; verify with `sqlmigrate` first.

## 6. CI invariants

```
uv run manage.py makemigrations --check --dry-run   # no model drift
uv run manage.py migrate                            # applies on sqlite (guards) / postgres (CI job)
uv run pytest -q                                    # full suite incl. migrations exercised
uv run ruff check .                                 # lint gate
```

## 7. Long-term hygiene

- Squash only after every deployed environment has the squashed head applied.
- Index renames: use `migrations.RenameIndex` (keeps both DB and state aligned).
- Never `unique=True` on a column that needs backfilled data in the same
  migration — add nullable, backfill via RunPython batches, then add the
  constraint in a follow-up migration.
